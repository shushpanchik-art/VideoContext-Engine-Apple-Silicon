# VCE: quality/speed benchmark harness

Этот инструмент создаёт воспроизводимую локальную оценку качества ASR и времени VCE. Он не запускает модели и не меняет движок: он сравнивает уже созданные выходные данные, чтобы сначала получить baseline, а затем оценивать новые настройки на тех же фрагментах.

## Что измеряется

- **WER** — доля word-level замен, удалений и вставок относительно ручного эталона. Для WER текст приводится к нижнему регистру, пунктуация превращается в разделитель, а последовательности пробелов нормализуются.
- **CER** — доля символьных ошибок после Unicode NFC, case-fold и нормализации пробелов. Пунктуация и разделители остаются, поэтому этот показатель чувствительнее к номерам стандартов, версиям и формулам.
- **Expected-term recall** — доля вручную заданных терминов, найденных как отдельные слова/фразы без учёта регистра и повторяющихся пробелов; совпадение внутри более длинного слова не засчитывается. Это не семантическая оценка.
- **RTF** — wall_seconds / video_seconds; меньше — быстрее. RTF < 1 означает быстрее реального времени. Если wall-clock не записан, RTF остаётся пустым.
- **Stage timings** — медианы поданных длительностей Whisper, Apple Vision OCR, FFmpeg/Tesseract OCR, VLM и других стадий. Стадии могут выполняться параллельно, поэтому их сумма не обязана равняться total wall-clock.

WER/CER не являются полноценной оценкой качества конспекта. Этот инструмент не измеряет галлюцинации модели, смысловую полноту, правильность описания слайдов или качество временного выравнивания. Для этого используй ручной [claim-level review checklist](../benchmarks/quality_review_template.csv): каждое спорное утверждение сопоставляется с конкретным ASR/OCR/кадром и временем.

## Запуск

1. Создай локальный каталог, который не попадает в Git, например benchmarks/private/.
2. Подготовь ручные эталонные транскрипции для 5–10 коротких отрывков: обычная речь, тихая речь, имена/аббревиатуры, числа и нормативы, технический текст на слайде. Храни точный текст отдельно от гипотезы. Не добавляй персональные или закрытые материалы в репозиторий.
3. Скопируй benchmarks/manifest.example.jsonl в benchmarks/private/manifest.jsonl и замени примерные пути/значения на реальные.
4. Для каждой версии (baseline/candidate) используй отдельный run_id, но сохрани одинаковые case_id и ссылки на один эталон. Прогоны должны использовать один и тот же набор видео, один и тот же профиль VCE и одинаковые условия, кроме конкретного изменяемого фактора.
5. Запусти:

   python3 scripts/vce_benchmark.py --manifest benchmarks/private/manifest.jsonl --out-dir benchmarks/private/results --baseline baseline-large

   Выходы: per_case.csv, summary.json, summary.md. Все отчёты остаются локальными.

## Формат JSONL

Одна строка на пару «test case × run». Обязательные поля: case_id, reference_text_path, и либо hypothesis_text_path, либо hypothesis_json_path + hypothesis_json_pointer. Все пути, не начинающиеся с /, разрешаются относительно директории manifest.

Пример JSON Pointer для структуры сегментов Whisper:
 /audio_transcript/segments/*/text

Опциональные поля:

- run_id (по умолчанию default)
- model, backend, profile
- video_seconds, wall_seconds
- stage_seconds: объект «название стадии → секунды»
- timings_json_path: путь к JSON с stage_seconds и необязательными wall_seconds / video_seconds (значения из этого файла используются, только если соответствующие поля не указаны в manifest)
- expected_terms: массив строк для контрольных терминов

Не указывай нулевые wall_seconds как заглушку: это будет измерено как реальное мгновенное выполнение и исказит RTF. Неизвестные замеры лучше оставить отсутствующими. Структура JSON VCE может отличаться между версиями, поэтому проверь путь к тексту в своём файле отчёта перед указанием JSON Pointer.

## Правила корректного эксперимента

- Сначала получить baseline на текущей рабочей конфигурации.
- Менять ровно один значимый фактор за раз: модель/бекенд ASR, OCR backend, количество кадров, разрешение или новый промпт.
- Для производительности выполнить по возможности два прогона каждого сценария и записать оба; один прогон может зависеть от прогрева модели и кэша.
- Не объединять silent video с обычным ASR-набором: пустой эталон исключает WER/CER, но полезен отдельной проверкой устойчивости.
- Сравнивать парные кейсы по case_id. В отчёте Δ WER/CER — candidate минус baseline (отрицательное число лучше), изменение RTF в процентах отрицательное означает ускорение.
- Проверять не только среднее по набору, но и per_case.csv: снижение средней ошибки может скрывать провал на одном важном термине.
- Сохранять TXT/JSON каждого прогона и не редактировать исходные транскрипты задним числом; все поправки эталона должны быть ревизионными.

## Текущий статус

Инструмент и unit tests автоматизированы. Фактическая база WER/CER и новый A/B замер не считаются проведёнными до запуска на локальных TXT/JSON и эталонах.
