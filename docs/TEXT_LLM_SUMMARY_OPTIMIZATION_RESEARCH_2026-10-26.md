# Исследование ускорения финального LLM-подытоживания VideoContext Engine

Дата: 2026-10-26  
Исходный код для анализа: опубликованный снимок `artifacts/source-snapshots/VideoContextEngine_v3.19.py` в коммите `1eb9295a65fb90da980d9104c80d65fbcbeec6c8`.  
Статус: исследование и план экспериментов; **код приложения этим документом не меняется**.

## Краткий вывод

Самые перспективные первые изменения — уменьшить объём генерируемого финальной LLM текста и проверить отключение thinking. В последнем полном прогоне Text LLM заняла 90.056 s; лог показывал приблизительно 3,737 выходных токенов при темпе около 40.9 токена/s. Это почти совпадает с длительностью стадии, поэтому генерация длинного ответа — сильный кандидат на главное узкое место финального этапа.

Текущий запрос Qwen3.5-9B делает значительно больше, чем «коротко подытоживает»: он генерирует executive summary, темы, общие тезисы, сущности, неопределённости и `scene_enrichment` для сцен. При этом описания сцен уже созданы VLM, а исходные транскрипт, OCR и временные метки должны сохраниться. В первую очередь следует сделать так, чтобы финальная LLM не переписывала каждую сцену при каждом запуске.

Приоритет:
1. Сначала точно измерить prefill, decode, output tokens, thinking и возможные повторные проходы.
2. Провести A/B с отключённым thinking, не меняя остальные параметры.
3. Реализовать экспериментальный режим **Fast Summary**, который генерирует только общий синтез и компактную структуру, сохраняя исходные данные сцен без изменений.
4. Уменьшить входной контекст за счёт удаления дублирования, а не грубого обрезания доказательств.
5. Затем сравнить Qwen3.5-4B и исследовать speculative decoding, только после проверки совместимости с установленной версией `mlx-vlm`.

Не следует начинать с изменения GPU/Metal-конфигурации: текущие измерения указывают на длительную генерацию крупного ответа, а не демонстрируют, что GPU целенаправленно не используется.

## 2. Что конкретно делает текущая Text LLM

Исследована функция `run_text_llm_postprocess()` в [снимке исходника](../artifacts/source-snapshots/VideoContextEngine_v3.19.py) (около строк 2814–3054):

1. Загружает модель через `mlx_vlm.load()` в каждом вызове.
2. Формирует JSON-контекст, включающий все сцены с транскриптом, OCR, визуальным описанием и тегами.
3. Сериализует контекст и старается уложить его в 47,000 символов, постепенно снижая пределы текстовых полей. Если контекст всё ещё слишком большой и сцен больше 80, остаётся выборка из 80 репрезентативных сцен.
4. Передаёт большой промпт, требующий строгий JSON с несколькими наборами полей.
5. Включает thinking в chat template и generation; задаёт thinking budget 512 токенов.
6. Ограничивает output generation 4,096 токенами.
7. После генерации парсит/валидирует JSON, согласует факты с аудио/OCR, канонизирует стандарты и выполняет итоговые проверки.
8. При невалидном JSON может использовать локальный `json_repair`, а если это не удаётся — сделать второй полный проход генерации для ремонта JSON.
9. В `finally` освобождает ссылки модели, вызывает `gc.collect()` и пытается вызвать `mx.clear_cache()`.

Промпт просит:
- `executive_summary` на 50–90 слов;
- до 15 тем;
- до 18 общих ключевых тезисов;
- сущности со списками scene IDs;
- неопределённости;
- `scene_enrichment` для каждой сцены: тема, описание на 1–2 предложения и до 3 тезисов.

Это не эквивалент компактного подытоживания: LLM заново пишет значительную часть информации, уже описанной VLM. На длинных роликах output size может расти почти линейно с количеством сцен.

Ещё один конкретный риск: в общем исключении вокруг `stream_generate` код обнуляет `raw`, а затем при пустом результате запускает `generate()`. Если поток завершился исключением после частичной работы, это потенциально может повторно выполнить дорогостоящую генерацию. Доказательств, что это произошло в последнем успешном прогоне, нет; стоит записывать счётчик и причину fallback.

## 3. Рекомендация №1 — отключить thinking в конечном структурировании

В исходнике оба явных места включают thinking:
- `apply_chat_template(..., enable_thinking=True)`
- `stream_generate(..., enable_thinking=True, thinking_budget=512)`

При этом комментарий рядом с реализацией уже говорит, что для этой ограниченной задачи извлечения следует избегать длинных reasoning-выводов. В конце кода удаляется блок `<think>...</think>`, но удаление после генерации не экономит токены, которые были потрачены до этого.

**Эксперимент A:** оставить модель, контекст, формат JSON и все ограничения прежними, но передавать `enable_thinking=False` при построении шаблона и при генерации. Сохранить совместимость с текущей установленной версией `mlx-vlm==0.7.10`: для случая, когда API не принимает аргумент, нельзя молча перейти на fallback, который снова включает thinking. Логировать, какой путь был реально выбран.

В текущей конфигурации budget составляет 512 thinking-токенов. При 40.9 токена/s это соответствует максимуму примерно 12.5 секунды декодирования, если бюджет полностью использован. Это лишь верхняя оценка потенциала: точное число фактически сгенерированных thinking-токенов пока отдельно не измерялось. Ускорение может быть меньше или практически отсутствовать.

**Проверка качества обязательна:** точность названий из OCR против ASR, чисел, стандартов, выявление фактического результата, корректные ссылки на scene IDs и отсутствие неподтверждённых выводов.

## 4. Рекомендация №2 — Fast Summary как лёгкий режим по умолчанию

Сохранить полный Deep Enrichment как опцию, но предложить отдельный Fast Summary. В быстром режиме финальная LLM должна возвращать только:
- компактное executive summary;
- темы, отражающие весь ролик;
- несколько наиболее важных общих тезисов;
- подтверждённые сущности;
- реальные расхождения и неопределённости.

Не требовать от неё `scene_enrichment` для каждой сцены. Оригинальные scene records остаются в выходном JSON с первичными полями `audio_transcript`, `ocr_text`, `visual_description`, `visual_tags`, исходными временными метками и ID. В Fast Summary LLM может добавлять глобальные выводы, но не должна переписывать эти поля.

Это, вероятно, главный рычаг сокращения decode time: уменьшить число токенов, которые модель должна выдать. Для 14-сценного запуска сокращение output вдвое теоретически может заметно уменьшить decode time, но фактическую экономию нельзя обещать до теста. Для сотен сцен эффект может быть существенно важнее, так как убирается повторное создание описания каждой сцены.

Перед внедрением нужно проверить функции `reconcile_text_llm_result()`, `_vce_v4_finalize_analysis_payload()`, JSON-валидацию, экспорт JSON/TXT и потребителей поля `enhanced_analysis.scene_enrichment`. В Fast Summary допустим пустой список enrichment только после того, как downstream-код явно поддерживает его, а интерфейс не обещает несуществующие улучшенные описания.

## 5. Рекомендация №3 — сократить input tokens и отделить prefill от decode

Сейчас JSON для LLM собирается с лимитами:
- транскрипт: до 600 символов на сцену;
- OCR: до 650;
- визуальное описание: до 650;
- до 12 тегов на сцену;
- существующая сводка: до 4,000 символов.

При длинном ролике это формирует большой prompt. Но грубо обрезать все строки небезопасно: можно потерять критически важные технические названия, числа и подтверждения из OCR.

Предпочтительнее сделать deterministic compaction:
- сохранять scene ID и time range;
- удалять дублирующие tags и формулировки, уже очевидные из описания;
- сокращать повторяющиеся части транскрипта, не удаляя новые факты;
- сохранять точные строки OCR с числами, именами продуктов, стандартами и техническими параметрами;
- ограничить количество глобальных тезисов и сущностей по явной схеме;
- измерять реальные input tokens через tokenizer совместимой модели, а не ориентироваться только на количество символов.

Сначала добавить метрики:
- `model_load_seconds`;
- `prompt_build_seconds`;
- `input_tokens`;
- `time_to_first_token_seconds` или `prefill_seconds`;
- `decode_seconds`, `output_tokens`, `decode_tokens_per_second`;
- `json_parse_seconds`, `validation_seconds`;
- `repair_attempts` и `fallback_after_stream_error`.

Это установит, что ограничивает оставшееся время после Fast Summary. Если prefill действительно велик на очень длинных видео, затем оценить hierarchical/map-reduce summarization: локальные короткие сводки блоков сцен с последующим общим синтезом. Не внедрять иерархическую схему до метрик: дополнительные LLM-вызовы сами создают задержку и могут оказаться хуже единого компактного запроса.

## 6. Ограничение output tokens и устойчивость JSON

В коде `generation_limit = max(1024, min(int(max_tokens), 4096))`. Последний прогон показал около 3,737 выходных токенов, поэтому важно проверить, насколько близко ответы подходят к верхнему пределу, завершается ли generation по EOS и не обрезается ли JSON.

Не следует просто снижать максимум токенов при сохранении нынешней схемы: это повышает риск незавершённого JSON и второго repair-pass. Правильная последовательность:
1. убрать лишние поля и ограничить длину ответа схемой;
2. попросить короткие значения, ограниченное число сущностей/тезисов;
3. контролировать EOS/truncation;
4. затем установить меньший `max_tokens`, достаточный для компактного формата.

Repair-pass следует измерять, а не просто удалять: если он редок, он не основная причина; если частый, может быть выгоднее улучшить schema/prompt и обрабатывать усечение отдельно.

## 7. Кэширование модели — для серии запусков, не главное для одного длинного видео

`run_text_llm_postprocess()` загружает модель во время этапа, а затем очищает ссылки и кеш. Сохранение модели в памяти может уменьшить cold-start время при последовательной обработке нескольких видео.

Но последний отчёт не даёт достаточного точного разложения 90.056 s между загрузкой и токеногенерацией, чтобы приписать основное время загрузке. Поэтому на одном ролике это не первый приоритет. На Mac с 32 GB нужно измерять unified-memory pressure при одновременном или последовательном хранении VLM, Text LLM и Whisper; персистентная загрузка всех моделей может ухудшить память или вызвать swap. Кэшировать только после отдельного теста cold vs warm и проверки, что VLM/Whisper не деградируют по памяти.

## 8. Тест более лёгкой модели Qwen3.5-4B

Существует `mlx-community/Qwen3.5-4B-MLX-4bit`, опубликованный как 4-битная MLX версия Qwen3.5-4B для Apple Silicon. Это реальный кандидат для сравнительного теста, а не гарантия эквивалентного качества. В текущем коде настройка модели Text LLM разрешает только `mlx-community/Qwen3.5-9B-MLX-4bit`, поэтому для эксперимента потребуется отдельная allowlist/ветка, без немедленной смены production default.

Сравнивать на одинаковых сохранённых inputs и схеме, с одинаковым температурным режимом и token limit. Проверить не только latency, но и:
- точность экранных написаний относительно ASR;
- правильность чисел, дат и технических стандартов;
- доказательность key points;
- связь утверждений со сценами;
- реальные неопределённости;
- валидный JSON;
- долю пропущенных важных событий.

В публичном community benchmark для Qwen3.5-9B-MLX-4bit на M1 Max 24-core GPU/32 GB с oMLX указывается около 44.3 токена/s при контексте 4K. Это ориентир другого runtime, версии ОС и профиля, а не прогноз VCE. Его полезность здесь — показать, что зафиксированные в VCE около 40.9 токена/s находятся в сопоставимом диапазоне и сами по себе не указывают на очевидно неисправный GPU-путь.

## 9. Speculative decoding — перспективно, но совместимость нужно подтвердить

Текущая документация проекта MLX-VLM описывает speculative decoding с draft-моделью; для некоторых поддерживаемых пар заявляется ускорение порядка 2–3×. Документационные примеры включают Qwen3.5-4B с `z-lab/Qwen3.5-4B-DFlash`. Это не подтверждает, что подходящая drafter-модель существует и совместима с используемой здесь Qwen3.5-9B-MLX-4bit.

Поэтому:
- не подключать произвольную 4B модель как drafter к 9B;
- сначала проверить API и реально доступные model/drafter pairs в **установленном** `mlx-vlm==0.7.10`, а не только в текущем README проекта;
- проверять exact-match/quality parity и фактический throughput на том же промпте;
- сначала протестировать после сокращения output, иначе можно оптимизировать уже устранённую лишнюю генерацию.

Это исследовательский вариант второй очереди, а не немедленное изменение.

## 10. Почему streaming сам по себе не ускоряет генерацию

Текущий код использует `stream_generate()`, чтобы обновлять прогресс, токены и приблизительную скорость. Streaming полезен для наблюдаемости и возможности показать первый результат раньше, но это не означает автоматически более высокий throughput. Если декодер всё равно должен сгенерировать 3,700 токенов, переключение на `generate()` без других изменений не сократит вычисление; наоборот, исчезнут промежуточные измерения. Важно оптимизировать количество токенов и runtime, а не менять API только ради скорости.

## 11. План A/B-валидации

Выполнять финальную LLM отдельно на сохранённых `final_segments` и `global_summary_text`, чтобы не ждать заново Whisper/VLM и не менять вход между вариантами. Локальные видео/транскрипты не загружать на GitHub; в CI тестировать mock-ответы, schema и parsing.

| Эксперимент | Единственное изменение | Что измерить |
|---|---|---|
| Baseline | Текущая реализация | Load, input tokens, TTFT, decode, output tokens, repair, quality |
| A | Thinking off | Разница времени / качества и действительно отключённый режим |
| B | Fast Summary без per-scene enrichment | Output tokens и decode time; неизменность исходных сцен |
| C | Compact context | Input tokens, TTFT/prefill и coverage доказательств |
| D | Qwen3.5-4B | Latency, memory, качество и точность JSON |
| E | Speculative decoding, только при подтверждённой паре | Throughput, принятие draft-токенов, качество и память |
| F | Keep model warm для серии роликов | Cold/warm latency, swap/pressure, влияние на прочие модели |

Рекомендовано минимум три повторения каждого варианта на идентичном сохранённом input с разделением cold/warm запусков. Записывать медиану и диапазон, а не только лучший результат. Отдельный длинный input должен содержать много сцен (включая более 80), чтобы проверить поведение текущего лимита/выборки сцен.

### Критерии принятия

- JSON валиден, без систематических repair-pass.
- Исходные транскрипты, OCR, визуальные описания и временные метки не модифицируются.
- В Fast Summary сохраняются ключевые глобальные факты, названия, числа, сущности и явные неопределённости.
- Не растёт количество неподтверждённых утверждений.
- Latency сравнивается по медиане на одинаковом входе, с явными cold/warm условиями.
- Прирост фиксируется только после измерения, не прогнозируется по чужому benchmark.

## 12. Рекомендуемая последовательность реализации

**P0 — диагностика без изменения результата:** записать фактические input/output tokens, TTFT, decode, load, JSON repair/fallback counters. Это минимально рискованно и делает дальнейшие результаты объяснимыми.

**P1 — thinking off A/B:** проверить совместимость `enable_thinking=False` и явно записать effective setting. Не менять промпт/схему одновременно.

**P2 — Fast Summary A/B:** добавить отдельный режим, сохранить Deep Enrichment как opt-in; проверить downstream-потребителей, интерфейс и JSON. Это кандидат на наибольшую экономию на длинных роликах.

**P3 — compact context и EOS/token budget:** сохранить факты и coverage; не просто обрезать строки.

**P4 — model/runtime experiments:** сравнить 4B, прогреть кэш для серий запусков, затем рассмотреть speculative decoding после проверки exact compatibility.

Ни одно из этих изменений в этом коммите не включается. PR остаётся в Draft, пока результаты A/B и качество не подтверждены на целевом Mac.

### Ограничения исследования

Числа, описанные как «наши измерения», взяты из сохранённого прогона от 2026-10-26. Публичные внешние benchmarks относятся к другим runtime/configurations и не дают гарантии ускорения в VCE. Предлагаемые выигрыши являются гипотезами для A/B, пока не измерены на одном и том же реальном входе. Устранение лишней генерации представляется более обоснованным первым шагом, чем замена всей модели или спекулятивное декодирование.
