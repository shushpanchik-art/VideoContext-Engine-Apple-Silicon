# Bounded frame prefetch и восстановление неподдерживаемого MP4

Этот набор патчей рассчитан на уже работающий локальный VideoContext Engine v3.19, в котором установлены патчи Metal/media recovery и parallel CPU Whisper + GPU VLM.

## Установка

После завершения активных задач и остановки VCE через кнопку интерфейса скачайте и запустите установщик из Terminal:

```bash
curl -fL --retry 3 \
  "https://raw.githubusercontent.com/shushpanchik-art/VideoContext-Engine-Apple-Silicon/feat/vce-parallel-cpu-asr-vlm-20261025/scripts/install_vce_prefetch_and_mp4_recovery.command" \
  -o "$HOME/Downloads/install_vce_prefetch_and_mp4_recovery.command" \
&& bash "$HOME/Downloads/install_vce_prefetch_and_mp4_recovery.command"
```

Установщик проверяет наличие проекта, Python virtualenv, валидность patcher-файлов и состояние порта 7555; затем запускает dry-run обоих патчеров. После просмотра diff нужно ввести `APPLY`. Скрипт не завершает работающий сервер автоматически, не перезаписывает исходные видеоролики и не изменяет пользовательские настройки. Он создаёт резервную копию движка; при ошибке установки исходный движок восстанавливается из неё.

## Что меняется

### Bounded keyframe prefetch

- Один CPU worker использует отдельный OpenCV `VideoCapture` для подготовки keyframes следующей сцены.
- Очередь ограничена одним ожидающим элементом; порядок сцен сохраняется.
- Если producer завершается с ошибкой, текущая/оставшиеся сцены читаются синхронно.
- Поток останавливается и присоединяется до очистки временного видео, чтобы не удалять файл, пока decode ещё выполняется.
- Stage timing включает `frame_prefetch_worker_seconds`, `frame_prefetch_wait_seconds` и `frame_prefetch_fallback_count`.

Prefetch не гарантирует ускорение: эффект зависит от времени декодирования и подготовки кадра по сравнению с VLM-инференсом. Следует проверить медиану полного времени 2–3 прогонов и не менять одновременно разрешение/число кадров.

### MP4 recovery и audio-only fallback

Для известных ошибок контейнера/кодека, включая `trun track id unknown`, `no tfhd was found`, `moov atom not found`, проблемы с decoder/codec parameters, VCE делает следующее:

1. Обычная проверка видео.
2. Временная копия через FFmpeg: сначала попытка H.264/AAC transcode, затем stream-copy remux; исходный файл не изменяется.
3. Если читаемый видеопоток получить не удалось, попытка извлечь аудио в отдельную временную дорожку и создать технический чёрный видеопоток для сохранения общей временной шкалы.
4. В audio-only fallback Whisper и сводка по аудио продолжают работать; VLM и OCR отключаются только для этой задачи.
5. Если не читается ни видео, ни аудио, VCE возвращает диагностическую ошибку. Ни один инструмент не сможет восстановить отсутствующие данные; повреждённый или неполностью скачанный файл нужно скачать/экспортировать заново.

Для восстановления нужен доступный в PATH исполняемый файл `ffmpeg`. Попытки ограничены timeout; перекодирование может занять дополнительное время и место во временной папке.

## Ручной тест после установки

1. Перезапустить `VideoContext Engine.app`.
2. Обработать короткий обычный MP4; проверить, что сцены и транскрипция сохранились и в логах появляются метрики prefetch.
3. Повторить обработку того же нормального ролика до/после prefetch с теми же настройками. Сравнивать полное wall time, а не только время VLM.
4. Повторить на проблемном VK MP4. В логах искать `[MP4 recovery]` или `[Audio-only fallback]`. При успешном аудио-only результате визуальные описания закономерно будут недоступны.
5. Если recovery завершается ошибкой, сохранить полный блок FFmpeg и проверить, удаётся ли независимо проиграть/перемультиплексировать файл. Не считать неуспех восстановления программной ошибкой, если у файла фактически отсутствует читаемый видеотрек и аудиоданные.

Патчеры валидируют Python AST до записи и делают резервные копии, но перед выпуском в `main` всё равно требуется тест на реальном Mac с пользовательским MP4.
