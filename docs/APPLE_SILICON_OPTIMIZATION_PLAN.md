# План оптимизации VideoContext Engine на M1 Max

Объект проверки: исходники пакета `9faf495`, локальный журнал первого прогона после установки и [diff PR #47](https://github.com/shushpanchik-art/VideoContext-Engine-Apple-Silicon/pull/47/files) на `9f0d5ac`. Числа ниже относятся к этим прогонам. Для нового baseline зафиксировать SHA исправления и SHA установленного языкового патча.

## Что уже известно

- Установленная копия, 14 сцен: 403,61 с от начала запроса, VLM inference 231,14 с (57,3%), загрузка VLM 5,28 с, Whisper 15,98 с загрузка и 27,16 с inference, Apple OCR 6,19 с. Text LLM выдала ответ, но reconciliation упал на `src`; HTTP 200 вернул базовый результат. Разницу между total и перечисленными стадиями нельзя целиком приписать Text LLM: часть работы перекрывается, а не все стадии разбиты. Этот прогон годится для выбора объекта профилирования, но не как эталон успешного анализа.
- В PR #47 MLX завершил анализ с Text LLM за ~313,43 с, а llama.cpp оборвался на native grammar stack после успешного MTMD preflight. Сравнить скорости по этим данным нельзя. Положительный preflight проверяет загрузку связки модель/mmproj в своём процессе. Он не доказывает ни сбой, ни исправность grammar в процессе сервера.
- Ранние замеры в `docs/APPLE_SILICON_BENCHMARKS.md` показывают, что изменение разбиения на сцены существенно меняет время VLM. Этот рычаг меняет объём анализа. В сравнении бэкендов сначала фиксировать сцены и кадры.
- Повторные загрузки Text LLM подтверждены кодом. Доля загрузки, вклад синхронизаций, давление на память, стоимость verbose-логов, доля CPU подготовки и эффективность `mx.compile` ещё не измерены.

## Карта кода и эксперименты

1. **VLM.** В `VideoContextEngine_v3.19.py` смотреть `MLXEngine.load_model/describe_scene/unload_model`, `LlamaCppEngine`, `get_vlm_engine` и цикл сцен `analyze_video`. Совпадающий путь пропускает загрузку на том же экземпляре MLXEngine, а режим памяти определяет время удержания модели. Измерить загрузку, извлечение и resize кадров, шаблон/процессор, prefill, decode, длину ответа и число повторов по сценам. Сравнить на одинаковых кадрах. Сначала анализировать 231,14 с VLM inference, затем отдельно проверять адаптивный выбор кадров с разметкой потерянных деталей.
2. **Text LLM.** `run_text_llm_postprocess` загружает модель и конфиг на каждый вызов, собирает контекст из сцен, стримит с thinking, при необходимости повторяет генерацию и очищает кеш MLX в finally. Отдельно измерить время ожидания `gpu_lock`, load, prompt/template, TTFT, decode, синтаксическое восстановление, повтор генерации и `vce_core.postprocess_text_llm_payload`. Кеш файлов HF и резидентная модель — два разных состояния. Для VLM и Text LLM прогонять комбинации «холодный процесс с локальными весами» и «повторный запрос в том же процессе». Сетевое скачивание считать отдельной метрикой.
3. **CPU/GPU и память.** `_vce_mlx_run` переносит ContextVar в однопоточный MLX executor. `_vce_prepare_mlx_vlm_runtime` меняет импорты и stream в mlx-vlm, обходит GPU device info и синхронизирует при возврате wired limit. `_VCEWhisperMLXCPU` использует CPU stream, а `analyze_video` сериализует GPU через `gpu_lock`. Снимать trace очереди, ожидание lock, CPU Whisper и интервалы GPU. Наличие overlap на CPU-часах и выбор устройства сами по себе не доказывают выигрыш. Перед переносом или удалением синхронизации воспроизвести работу на закреплённых версиях и после холодного запуска. Проверить, возвращается ли wired limit при ошибке synchronize; исправлять отдельно от ускорения.
4. **Ошибки Metal.** `_vce_describe_scene_with_memory_fallback` различает timeout и OOM. Timeout завершает VLM для ролика, OOM пробует уменьшенные кадры. Записывать каждую попытку с исходными и фактическими параметрами, типом сбоя и временем. Базовый отчёт после fallback считать частичным. Различать OOM, GPU timeout, native abort, сетевой разрыв и ошибки JSON. Использовать stdout/stderr только текущего процесса/прогона, чтобы прежние строки MTMD не влияли на вердикт.

## Проверка противоречий PR #47

- **OCR-кеш.** В #47 отключение обоих кешей было условием паритета. На текущей ветке `enable_ocr_cache` — настройка запроса с дефолтом false. В `analyze_video` она выбирает кешируемый путь только для Apple Vision OCR. Observer передаёт значение и сохраняет фактические поля. В baseline явно ставить false в обеих группах и сверять `request_fields`. Отдельный эксперимент с true требует счётчиков hit/miss и одинаковой последовательности запросов.
- **Лимит.** В #47 default 4096, в текущем движке default и верхняя граница API 8192, а primary и model repair используют `generation_limit`. `n_ctx` Text LLM и контекст smoke-теста измерять отдельно от лимита выхода. Для GGUF фиксировать токенизированный ввод, доступное окно, запрошенный бюджет, фактические токены и finish_reason. Обрыв по length отличается от отсутствия начальной скобки и от аварии native runtime.
- **JSON repair.** `_text_llm_find_json_candidate_offset` отсеивает посторонние скобки. Нет кандидата → model repair пропускается. При ошибке парсинга синтаксический helper опционален, затем возможен один вызов модели. Проверить наличие `json_repair` в обоих окружениях и фиксировать parse/repair исход. Если helper вернул dict, а последующая валидация его отклоняет, текущая ветка не попадает в model repair; покрыть отдельной фикстурой до смены политики. Сравнивать долю валидных первичных JSON, стоимость исправления и сохранность фактов.
- **Диагностика.** `_vce_llama_json_completion` текущего движка не передаёт `response_format` или native grammar, поэтому старый crash не доказывает проблему текущего режима. Watchdog уже распознаёт native abort. Observer до исправления искал общий текст `mtmd context`, включая положительный preflight. Добавлен отдельный verdict для наблюдаемого grammar stack abort и сужен MTMD-классификатор. Проверить актуальные fault fixtures и повторить реальный прогон в отдельном процессе. HTTP 200 с провалом Text LLM не считается успешным.
- **Артефакты.** NSR observer задаёт `generate_json=false`, чтобы не писать рядом с видео, и сохраняет API response в каталоге запуска. Проверять наличие `response.json`, валидного Text LLM результата и полноту манифеста. Публикация логов и материалов за рамками локального A/B.

## Инструменты и применимость

- [MLX 0.32.4: streams](https://ml-explore.github.io/mlx/build/html/python/devices_and_streams.html), [управление памятью](https://ml-explore.github.io/mlx/build/html/python/memory_management.html), [компиляция](https://ml-explore.github.io/mlx/build/html/usage/compile.html). Собирать active/cache/peak отдельно от RSS, swap и давления системы. `mx.compile` проверять на одной измеренной функции MLX с повторяющимися формами, отдельно учитывать компиляцию и синхронизировать границы микробенча. Весь Python pipeline с I/O, стримом и постобработкой не является кандидатом.
- [Instruments / Metal System Trace](https://developer.apple.com/documentation/metal/metal-developer-workflows) и `xctrace list templates` — первый способ подтвердить idle GPU, барьеры и реальные интервалы команд. Собирать короткий trace отдельно от итоговых замеров. [actop](https://github.com/binlecode/actop) — опциональный обзор SoC, температуры и полосы памяти, не доказательство длительности отдельного kernel или принадлежности нагрузки конкретному запросу.
- [mlx-profiler](https://pypi.org/project/mlx-profiler/) — диагностический Python-профайлер операций. Точные GPU timestamps перечислены в roadmap. Сверить overhead с uninstrumented прогоном и Instruments. [swift-mlx-profiler](https://github.com/VincentGourbin/swift-mlx-profiler) — отдельный Swift-проект; VCE запускает инференс из Python, поэтому Swift-интеграция сейчас не нужна.
- [phew](https://github.com/0xClandestine/phew) — поиск оптимизаций для изолированного MLX кода. Пробовать только после профиля, в отдельной среде, на фиксированных формах, dtype и допусках. Предложение инструмента должно пройти VCE A/B и проверку качества.
- Точное происхождение названий `mlx-performance-audit` и «Metal Floor» как отдельных инструментов не подтверждено. Для development skills найден [mlx-agentic-development](https://github.com/alpharomercoma/mlx-agentic-development). Его инструкции и probes можно ревьюить как сторонние исходники. В протоколе «Metal floor» означает измеренный низкоуровневый контроль на том же M1 Max, например [llama.cpp](https://github.com/ggml-org/llama.cpp) с `llama-bench` для text prefill/decode. Это не VCE wall time и не доказательство потолка VLM.

## Сравнение бэкендов

- **MLX/Metal** — контрольная продуктовая реализация для VLM и Text LLM. Исправленный end-to-end прогон является первым допуском.
- **llama.cpp/Metal** — сравнивать после text-only JSON smoke, отдельного MTMD preflight и полного успешного прогона. Зафиксировать revision GGUF, mmproj, llama-cpp-python/native библиотек, контекст и offload. При различной квантизации маркировать сравнение как сравнение готовых конфигураций, а не чистый эффект backend. Отдельно проверить единый backend и при необходимости гибрид VLM MLX + Text LLM llama.cpp в стенде.
- **PyTorch MPS** — в текущей ветке нет эквивалентного VLM/Text LLM backend, PyTorch/MPS используется в пути Whisper. Для LLM нужен отдельный проверенный адаптер под ту же архитектуру и доступную сопоставимую точность. Проверить CPU fallback, MPS memory и [MPS profiler](https://docs.pytorch.org/docs/stable/generated/torch.mps.profiler.profile.html). Если модель не помещается или поддержка отсутствует, записать это как результат совместимости; скорость MPS Whisper сравнивать отдельно при одинаковой модели и настройках ASR.

## Последовательность небольших PR

1. **Диагностика и воспроизводимый baseline.** `analyze_video`, `run_text_llm_postprocess`, observer/watchdog. Добавить монотонные таймеры, конфигурацию, cold/warm, явный статус частичного анализа, артефакты без исходного видео. Эффект — сопоставимые цифры. Риск — overhead/публичная схема; диагностические поля хранить в стенде, откат выключателем instrumentation.
2. **Цена сцены.** `MLXEngine.describe_scene`, выбор/предзагрузка кадров и цикл VLM. Сначала фиксированный ввод и профиль, затем один эксперимент с подготовкой кадров или повторным использованием неизменяемого prompt/template. Риск — память и перепутанный порядок кадров. Откат к прежнему пути по флагу.
3. **Жизненный цикл модели.** `MLXEngine.load_model/unload_model` и `run_text_llm_postprocess`. Сначала проверить раздельно CPU-конфиг/процессор и резидентную модель. Только при измеримой цене загрузки добавить ограниченный warm cache для режима с достаточной памятью, с ключом backend/model/revision/device/context и явным eviction перед несовместимой нагрузкой. Риск — swap/OOM, неверное переиспользование и конкуренция. Откат к load/release на запрос и сброс кеша.
4. **Потоки и совместимость MLX.** `_vce_prepare_mlx_vlm_runtime`, `_VCEWhisperMLXCPU`, `_vce_clear_metal_memory_caches`. Изолировать shim по версии, восстановление wired limit гарантировать даже при исключении, проверять последовательный и параллельный профили. Смена количества sync требует trace и воспроизведения отказа. Откат на закреплённую реализацию и последовательный профиль.
5. **Text LLM и бэкенды.** `run_text_llm_postprocess`, `_vce_llama_json_completion`, `tools/bench/bench_text_llm_summary.py`. A/B по одному фактору: thinking, длина контекста, затем repair. В отдельном PR сравнить полные конфигурации, продвигать backend только после повторяемого выигрыша. Риск — рост невалидных JSON и потеря доказательных деталей. Откат прежним профилем/бюджетом.
6. **Ядра по данным профиля.** Изолированный эксперимент `mx.compile` или phew после PR 1–5 и только для измеренного участка. Риск — цена перекомпиляции на разных формах, ошибки численной эквивалентности, зависимость от поколения GPU. Откат удалением экспериментального варианта, исходный путь остаётся baseline.

## Протокол допуска

- На M1 Max зафиксировать macOS, версии пакетов, SHA, модели/ревизии, квантизацию, GPU offload, лимиты, настройки OCR/ASR, хеш ролика и manifest сцен/кадров. Локальные наборы: короткий общий ролик, длинный с плотным OCR, NSR на 14 сцен, случай с нестандартным входом и тест отмены. Веса скачаны до замеров; питание и режим системы неизменны, фоновые тяжёлые процессы исключены.
- 1 прогрев и минимум 5 пар AB/BA на workload для первичного вывода. Для P95 собрать не менее 20 успешных измерений и указывать также число ошибок/частичных прогонов по всем попыткам. Cold process и warm requests измерять отдельно. Сохранять JSONL с отдельными временами стадий, TTFT/prefill/decode, tok/s, wall time, peak MLX, RSS, swap delta, thermal state и типом ошибки. Для распараллеливания сравнивать критический путь, а не сумму длительностей.
- Предложенные пороги первого этапа: медиана полного анализа быстрее минимум на 10% на целевом наборе с устойчивым направлением парных дельт; ни один обязательный workload не хуже более чем на 5% по медиане; P95 не хуже более чем на 10%; пик памяти не выше более чем на 5% и без систематического роста swap при повторных запросах. Если разброс перекрывает эффект, расширить выборку, не менять default.
- На обязательных прогонах ноль native abort, GPU timeout и необъяснённых fallback. Отдельно проверить отмену, повтор после отказа, 3 последовательных длинных запроса, отсутствие чужой диагностики, полный JSON, привязки сцен, канонические имена, речь/OCR/видео и базовый отчёт при контролируемом отказе. Парное ручное ревью по фиксированной рубрике качества. Каждый PR приносит raw timings, сводку и команду/флаг отката.
